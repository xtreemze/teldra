# ADR 0009: Appearance and baked-lighting interchange

Status: accepted

## Decision

Teldra separates ordinary material appearance from optional high-quality baked lighting.

- glTF/GLB remains the web geometry/material transport.
- `appearance.manifest.json` records the portable material profile and texture semantics expected by exporters/renderers.
- `lighting.manifest.json` records derived radiance bases and reflection-probe states generated by Blender/Cycles or another compatible offline pipeline.
- `quality/asset-interchange.json` is the machine-readable interchange profile shared by exporters, build tooling, fixtures, and renderer certification.
- Neither manifest nor derived asset becomes architectural or automation authority.

## Material profile and color management

The first profile follows glTF metallic-roughness PBR:

- primary material coordinates use UV set 0;
- baked lighting uses UV set 1;
- the portable radiance working space is linear-sRGB;
- base-color and emissive color textures use sRGB transfer;
- normal, occlusion, metallic, and roughness data are linear;
- metallic/roughness packing is G=roughness, B=metallic.

Texture bindings may point to external assets when needed, but the GLB remains free to embed ordinary material textures. The manifest exists to make interchange assumptions explicit and testable, not to duplicate the glTF material graph.

Display tone mapping, exposure, HDR output mapping, and monitor color management are renderer/presentation policy. They must not alter portable material or baked-radiance semantics.

## UV responsibilities

UV0 is owned by ordinary material appearance.

UV1 is reserved for baked-lighting lookup for assets that participate in baked radiance. A bake/export pipeline may generate or repack UV1, but doing so changes a derived input and therefore invalidates the associated baked assets.

Runtime renderers must not infer a lightmap UV set from mesh ordering or importer defaults.

## Mesh, material, and canonical identity

Scene `nodeKey` is the portable render-part identity.

- glTF node/mesh names may change during export or optimization;
- Blender object/collection names are authoring conveniences;
- Babylon mesh IDs are runtime implementation details;
- none of those names may replace `nodeKey`.

The GLB exporter preserves `nodeKey` through `extras.teldra` as defined by ADR 0008.

`materialKey` is the portable semantic identity for an appearance binding. glTF/Blender/Babylon material names may differ and are non-authoritative.

Compression or mesh merging is permitted only when every resulting render part can still resolve to the same canonical identity and transform semantics.

## Radiance bases

Indirect/diffuse baked lighting is represented as a linear additive basis:

```text
final indirect radiance =
    ambient
  + daylight × daylight factor
  + Σ fixture-basis × runtime intensity × runtime tint
```

All runtime addition happens in linear-sRGB.

A basis may represent one fixture or a group of fixtures whose indirect contribution is intentionally shared. `referenceIntensity` defines the authored bake intensity represented by a coefficient of 1.0.

A light ID may belong to at most one fixture-group basis in one manifest. This avoids accidental double-counting. Ambient and daylight bases normally have no device light IDs.

## Tinting

`tintable=true` means the runtime may multiply the neutral baked contribution by the live light color. It is an approximation for colored indirect light and does not assert spectral equivalence to a new Cycles render.

Where that approximation is inadequate, a future schema revision may introduce multiple sampled color bases. Version 0.1.0 must not silently invent those semantics.

## Reflection probes

Specular reflections are not additive lightmaps.

Each probe has a canonical project-space position and influence volume. A probe may have several prefiltered states such as daylight/evening. Runtime state chooses or cross-fades those states through a renderer projection; Home Assistant entity IDs and automation rules do not belong in the lighting manifest.

Mirrors or other view-dependent exceptional surfaces remain runtime renderer concerns.

## Optimization and compression stages

The portable pipeline order is:

1. canonical IFC/twin inputs;
2. scene export;
3. canonical identity annotation;
4. appearance binding;
5. optional lighting bake;
6. geometry optimization/compression;
7. texture compression;
8. final artifact hashing and provenance.

Identity annotation precedes geometry optimization so meshopt, Draco, mesh merging, or future optimizers cannot become identity authorities.

GLB is the baseline geometry container. Meshopt and Draco are optional delivery stages, not canonical formats. Any optimizer must preserve canonical-to-scene transforms and stable render-part identity.

Web texture delivery targets KTX2. The codec profile is a build/policy choice; changing it invalidates the derived artifact but does not change material/radiance meaning.

Reference-quality intermediates such as EXR may exist in the bake workspace but are not portable runtime assets.

## Deterministic invalidation

Derived outputs are reusable only when artifact provenance and all relevant inputs match.

Invalidating inputs include:

- source geometry hash;
- scene-manifest hash;
- appearance-manifest hash;
- UV layout;
- material semantics;
- lighting groups;
- bake settings;
- producer/tool versions;
- toolchain-manifest hash;
- compression settings.

The artifact-provenance contract from ADR 0016 is the cache authority. Filenames are not cache identities.

The lighting manifest additionally binds its output to the scene/appearance hashes, bake settings, Blender/Cycles/pipeline versions, and settings hash.

## Reference certification

Golden Home is the deterministic interchange-contract fixture.

CI verifies that:

- every appearance material targets an existing scene `nodeKey`;
- every radiance basis targets existing scene identities;
- fixture-group light IDs resolve to canonical twin device IDs;
- material textures use UV0;
- radiance bases use UV1;
- baked/probe runtime textures use KTX2;
- color-transfer semantics agree with the machine-readable profile;
- compression cannot replace canonical identity.

The existing Babylon certification proves that the GLB/scene-manifest identity path resolves canonical objects correctly.

Blender 4.5.14 LTS is the first certified offline reference producer. The dedicated certification workflow downloads the exact official Linux x64 artifact, verifies it against Blender's versioned upstream SHA-256 manifest, and requires build hash `62c1db4208e8`. It then:

- runs a deterministic headless CPU Cycles reference render;
- exports GLB with UV0, UV1, metallic-roughness material semantics, and nested `extras.teldra` identity;
- loads that generated GLB through the real Studio `TwinViewport` and Babylon runtime in Chromium;
- proves project-to-screen-to-pick canonical identity round-trips;
- captures the Babylon canvas and compares luminance, contrast, and blue-material bias against versioned tolerances;
- compares the Babylon and Cycles reference metrics using an explicitly bounded cross-renderer tolerance rather than requiring pixel identity between different renderers.

The certified producer, observed metrics, and tolerances live in `integrations/blender/reference-toolchain.json`. Any Blender/Cycles version, build hash, material/UV behavior, Babylon identity behavior, or visual metric outside those bounds fails certification and requires an explicit baseline review.

## Identity

Radiance bases target stable scene-manifest `nodeKey` values. They must never target transient Babylon mesh IDs or array indices.

Canonical light IDs identify runtime light contributions. External platform IDs such as Home Assistant entities remain adapter bindings outside this contract.
