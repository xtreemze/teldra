# ADR 0009: Appearance and baked-lighting interchange

Status: accepted

## Decision

Teldra separates ordinary material appearance from optional high-quality baked lighting.

- glTF/GLB remains the web geometry/material transport.
- `appearance.manifest.json` records the portable material profile and texture semantics expected by exporters/renderers.
- `lighting.manifest.json` records derived radiance bases and reflection-probe states generated by Blender/Cycles or another compatible offline pipeline.
- Neither manifest becomes architectural or automation authority.

## Material profile

The first profile follows glTF metallic-roughness PBR:

- primary material coordinates use UV set 0;
- baked lighting uses UV set 1;
- base-color and emissive color textures use sRGB transfer;
- normal, occlusion, metallic and roughness data are linear;
- metallic/roughness packing is G=roughness, B=metallic.

Texture bindings may point to external assets when needed, but the GLB remains free to embed ordinary material textures. The manifest exists to make interchange assumptions explicit and testable, not to duplicate the glTF material graph.

## Radiance bases

Indirect/diffuse baked lighting is represented as a linear additive basis:

```text
final indirect radiance =
    ambient
  + daylight × daylight factor
  + Σ fixture-basis × runtime intensity × runtime tint
```

All runtime addition happens in linear-sRGB.

A basis may represent one fixture or a group of fixtures whose indirect contribution is intentionally shared. `referenceIntensity` defines the authored bake intensity represented by a coefficient of 1.0.

A light ID may belong to at most one fixture-group basis in one manifest. This avoids accidental double-counting. Ambient and daylight bases normally have no device light IDs.

## Tinting

`tintable=true` means the runtime may multiply the neutral baked contribution by the live light color. It is an approximation for colored indirect light and does not assert spectral equivalence to a new Cycles render.

Where that approximation is inadequate, a future schema revision may introduce multiple sampled color bases. Version 0.1.0 must not silently invent those semantics.

## Reflection probes

Specular reflections are not additive lightmaps.

Each probe has a canonical project-space position and influence volume. A probe may have several prefiltered states such as daylight/evening. Runtime state chooses or cross-fades those states through a renderer projection; Home Assistant entity IDs and automation rules do not belong in the lighting manifest.

Mirrors or other view-dependent exceptional surfaces remain runtime renderer concerns.

## Deterministic invalidation

The lighting manifest binds its output to:

- scene-manifest hash;
- appearance-manifest hash;
- bake-settings hash;
- Blender version;
- Cycles version;
- Teldra bake-pipeline version;
- pipeline settings hash.

Every emitted texture also carries a SHA-256 hash.

Changing geometry, UVs, materials, lighting groups, bake settings, or the producing toolchain must therefore invalidate affected derived outputs rather than mutating canonical project data.

## Compression and delivery

Web delivery targets KTX2. The schema deliberately records the asset container rather than hard-coding a specific KTX2 codec profile; codec choice is a build/policy concern and may evolve without changing radiance semantics.

Reference-quality intermediate files such as EXR may exist in the bake workspace but are not part of the portable runtime lighting manifest.

## Identity

Radiance bases target stable scene-manifest `nodeKey` values. They must never target transient Babylon mesh IDs or array indices.

Canonical light IDs are used only to identify runtime light contributions. External platform IDs such as Home Assistant entities remain adapter bindings outside this contract.

## Executable reference certification

The interchange contract is certified by `integrations/blender/reference/generate.py` and the checked-in fixture under `fixtures/blender/reference/`.

The reference pipeline runs in Blender 5.2.2 LTS and proves, with generated bytes rather than hand-authored manifest claims:

- canonical right-handed Z-up metre geometry is exported through Blender's glTF/GLB exporter;
- glTF node `extras.teldra` preserves the renderer-neutral `nodeKey`, canonical ID, and IFC GlobalId;
- UV0 and UV1 survive as `TEXCOORD_0` and `TEXCOORD_1`;
- Principled BSDF base color, metallic, and roughness arrive as glTF metallic-roughness factors without an undocumented conversion layer;
- Cycles can bake a tiny diffuse-light reference texture using UV1;
- the emitted scene manifest records the GLB hash and canonical-to-glTF coordinate transform;
- the exact generated GLB is loaded by Babylon in Storybook and a projected surface point round-trips through picking to the same canonical identity.

The checked-in bake is a small PNG reference intermediate because the purpose of this fixture is to certify Blender/Cycles bake semantics. Runtime baked-lighting delivery remains KTX2. Choosing and changing a KTX2 codec profile remains a build-policy concern and must not alter the radiance semantics defined above.
